# PRD: 服务端首次认领与一键配对（Claim-based Pairing）

## 1. 背景与痛点

在当前的同步架构中，同步服务端依赖预设的 `NEXTDO_OWNER_TOKEN`。用户必须先在部署环境手工配置 64 位 Hex 密钥，再在第一台客户端手动抄写并粘贴。这一流程存在显著痛点：
1. **首次配置摩擦极大**：即便支持了连接串和二维码，首台设备依然需要手动填入 Token；
2. **缺乏自举能力**：无法做到“第一次点击按钮，系统随机生成 Token，之后使用二维码同步”。

## 2. 目标

1. **服务端支持待认领（Unclaimed）模式**：未预设静态 Token 时，允许第一台接入的设备通过一次性认领接口初始化，并由系统自动生成 Token；
2. **防抢占与安全性**：认领操作必须是原子的、一次性的。一旦被认领，服务端立即锁定该接口，后续请求全部拒绝；
3. **客户端一键初始化**：在未连接状态下，用户只需输入服务器地址并点击「连接」，系统自动探测：若未认领则一键自动生成并完成绑定，直接进入已连接状态；
4. **无缝多端互联**：首台设备绑定后，直接展示二维码与复制连接串，后续设备扫码即连；
5. **完全向后兼容**：继续支持现有环境变量静态指定 Token 的部署模式。

## 3. 非目标

- 不引入复杂的 OAuth、公有云多租户注册体系（保持本地优先与自托管轻量特性）；
- 不做 Token 在线找回（丢失后需由部署管理员重置）。

## 4. 功能设计与接口定义

### 4.1 服务端端点

1. `GET /claim/status`（无需鉴权）
   - 响应：`{ claimed: boolean }`
2. `POST /claim`（无需鉴权，仅 `claimed === false` 时允许）
   - 请求体（可选）：`{ ownerToken?: string }`（可由客户端生成，缺省时由服务端使用安全随机数生成 64-hex Token）
   - 响应（成功）：`200 { ok: true, ownerToken: string }`
   - 响应（已被认领）：`409 { error: "already_claimed", code: "claim.already_claimed" }`

### 4.2 客户端流程

1. 用户输入服务器地址，Token 留空，点击「连接」；
2. 客户端向服务器请求 `/claim/status`：
   - 若 `claimed === false`：自动发起 `POST /claim`，取得新生成的 Token，存入本机并自动建立连接；
   - 若 `claimed === true`：内联提示“该服务器已被认领，请使用已配对设备扫码或输入 owner token”。
3. 若用户填入了 Token 或粘贴了连接串，直接走原有连接流程。

## 5. 验收标准

- [ ] 服务端在未设置环境变量时启动进入未认领状态，`GET /claim/status` 返回 `false`；
- [ ] 调用 `POST /claim` 成功返回安全随机 Token 并持久化存储，后续 `GET /claim/status` 返回 `true`；
- [ ] 再次调用 `POST /claim` 返回 409 且不篡改原有 Token；
- [ ] 设置了静态 `NEXTDO_OWNER_TOKEN` 时，`claimed` 始终为 `true`，`POST /claim` 被拒绝；
- [ ] 客户端在空 Token 状态下一键连接未认领服务器，自动完成绑定并成功连接；
- [ ] 单元测试全覆盖（服务端、数据层与移动端）。
